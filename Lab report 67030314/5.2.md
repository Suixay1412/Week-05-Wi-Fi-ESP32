## 3. คำถามท้ายการทดลอง (Post-Lab Questions)

1. เหตุใดการระบุ SSID ผิด (ข้อ 5.2.2) จึงส่งผลให้เกิด Disconnect Event ด้วย Reason Code `201` (`WIFI_REASON_NO_AP_FOUND`) ตั้งแต่เฟส Scan?
ตอบ เพราะ ESP32 จะสแกนหา BSSID/SSID เป้าหมายในอากาศก่อน เมื่อไม่พบ AP ที่มีชื่อตรงกับเงื่อนไขในเฟส Scan จึงไม่สามารถเข้าสู่เฟส Authentication ได้ และสั่งปล่อย Disconnect Event ออกมาทันที

2. เหตุใดการพิมพ์ Password ผิด (ข้อ 5.2.3) จึงผ่านเฟส Auth และ Assoc มาได้ แต่มาล้มเหลวในเฟส 4-Way Handshake (Reason Code `15` หรือ `204`)?
ตอบ เพราะในมาตรฐาน 802.11 เฟส Auth/Assoc เป็นแบบ Open System ซึ่งตกลงแค่คุณสมบัติการผูกสัมพันธ์ระดับ Link-Layer โดยยังไม่มีการตรวจรหัสผ่าน รหัสผ่านจะถูกนำมาคำนวณคีย์เพื่อตรวจสอบ MIC ในเฟส 4-Way Handshake เมื่อรหัสผ่านผิด การตรวจสอบ MIC จึงล้มเหลวและเกิด Timeout (Reason Code 15)

3. ลำดับการเกิด Event ระหว่าง **`WIFI_EVENT_STA_CONNECTED`** กับ **`IP_EVENT_STA_GOT_IP`** Event ใดเกิดขึ้นก่อนกัน และมีความหมายทางกายภาพของ Layer Network ต่างกันอย่างไร?
ตอบ `WIFI_EVENT_STA_CONNECTED` เกิดขึ้นก่อน โดยแสดงถึงความสำเร็จในระดับ Layer 2 ส่วน `IP_EVENT_STA_GOT_IP` เกิดตามมาทีหลังเมื่อแลกเปลี่ยนคีย์ความปลอดภัยและได้รับ IP Address จาก DHCP Server เรียบร้อยแล้ว ซึ่งแสดงถึงความพร้อมในระดับ Layer 3

4. สมาชิกตัวแปร `reason` ในโครงสร้าง `wifi_event_sta_disconnected_t` มีประโยชน์อย่างไรต่อการออกแบบระบบค้นหาสาเหตุและกู้คืนการเชื่อมต่อ (Auto-Reconnection Mechanism) ในแอปพลิเคชัน IoT?
ตอบ ช่วยให้อุปกรณ์ IoT จำแนกประเภทความผิดพลาดเพื่อการกู้คืนระบบได้อย่างถูกต้อง เช่น หาก Reason คือ `NO_AP_FOUND` สัญญาณอาจจะหลุดชั่วคราว ให้สั่งสแกนหรือเชื่อมต่อใหม่ แต่หาก Reason คือ `HANDSHAKE_TIMEOUT` (รหัสผ่านผิด) ระบบควรถอนการเชื่อมต่อและแจ้งเตือนผู้ใช้งานให้ป้อนรหัสผ่านใหม่ แทนที่จะกดต่อวนซ้ำไร้ประโยชน์
